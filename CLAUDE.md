# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**66** is a Bible-quiz game (named for the 66 books of the Bible). It has two modes:
- **Bible Blitz**: a solo chariot race against bots. It runs entirely on the client and works offline.
- **Open Arena**: a Kahoot-style hosted multiplayer game. The server holds the authoritative state, players join by room code or QR, and a spectator board is available.

`PLAN.md` (gitignored, local only) holds the product/architecture plan. Code comments refer to its sections, e.g. "PLAN.md §6".

## Commands

This is an npm workspaces monorepo (`app`, `server`, `shared`). Run commands from the repo root:

```bash
npm install
npm run dev:app        # Vite dev server; proxies /socket.io and /api to :3066
npm run dev:server     # arena server (tsx watch) on :3066 (PORT env overrides)
npm run build          # app: tsc -b && vite build → app/dist
npm run start          # server; also serves app/dist if it exists
npm run lan            # build app + start server → play over wifi via printed LAN URL / QR

npm run lint --workspace app
npm run typecheck --workspace server
npm run i18n:check --workspace app   # translations complete (docs/i18n.md)
```

There is no test suite. The checks are type-checking (`npm run build` for the app, `typecheck` for the server) and lint.

Native shells: Capacitor (`app/ios`, `app/android`, `webDir: dist`). After a build, sync with `npx cap sync` from `app/`.

Art pipeline (run from `art-pipeline/`, which has its own `npm install` for `sharp`; see its README). Generates images with Google's Nano Banana model. The key goes in the gitignored `art-pipeline/.env.local`. Calls are paid (about $0.03 per image), so use `--dry-run` first:
```bash
node generate.mjs --dry-run                 # print the prompts from prompts.json, no API calls
node generate.mjs --only=<asset> --count=3  # candidates → out/ (raw originals kept in out/raw/)
node contact-sheet.mjs <prefix>             # side-by-side review sheets → out/_sheet-*.png
```
Copy the chosen images into `app/public/art/` as trimmed WebP.

Question pipeline (plain Node scripts, run from `question-pipeline/`; see its README for batch format and rules):
```bash
node scripts/fetch-bible.mjs   # once: WEB Bible corpus → data/web-bible.json
node scripts/verify.mjs        # data/generated/*.json → verified / review-queue / rejected
node scripts/review.mjs        # interactive: approve/reject review-queue items (a/r/s/q)
node scripts/compile.mjs       # verified + approved-manual → app/src/questions/bank.json + verses.json
```

## Architecture

- **`shared/`** (`@sixtysix/shared`) is TypeScript source with no build step. Vite resolves it through the workspace, and the server resolves it through a tsconfig `paths` entry and runs it with `tsx`. It contains:
  - `protocol.ts`: the socket.io event maps (`ClientToServerEvents` / `ServerToClientEvents`), `RoomState`, and `ArenaPhase`. **Any change to arena messaging starts here.**
  - `scoring.ts`: `scoreAnswer` (500 base + up to 500 speed bonus over `QUESTION_TIME_MS`). The app (`app/src/game/scoring.ts` re-exports it) and the server use it, so both compute scores identically.
  - `question.ts`: the `Question` type.
- **Question bank**: `app/src/questions/bank.json` (about 5,500 questions) and `verses.json` (the cited verse text for each question id) are generated by `question-pipeline/compile.mjs`, so don't edit them by hand. The app loads `bank.<locale>.json` (the same questions with only that language and English, written by `compile-i18n.mjs`) lazily as its own chunk; the server sends the verse text in `game:reveal`. The app bundles it through `questions/provider.ts` (the `QuestionProvider` abstraction). The server reads the same file from disk in `server/src/bank.ts`.
- **App** (`app/src`): React 19 + Zustand. There is no router. `App.tsx` maps the `screen` value in `game/store.ts` to a component, and you navigate with `useGameStore.getState().goTo(screen)`. `main.tsx` parses the deep links `/join/CODE` (prefills the arena join flow) and `/board/CODE` (spectator), then resets the URL to `/`.
  - `game/store.ts`: the Bible Blitz race state machine (reading → question → reveal → progress → podium) with local timers, bots (`bots.ts`), and the player profile. Persistence in `persistence.ts` uses versioned `localStorage` keys (`sixtysix.*.v1`), including the stable device UUID that serves as arena identity.
  - `arena/arenaStore.ts`: the socket.io client and all live arena state. Its role is `host | player | spectator`. Host and spectator views get the wide layout (`app-wide`) because they are meant for projectors. A reload lands back in the game: the room and role are kept in `sixtysix.arenaSession.v1` (6 h) and `resume()` (called from `main.tsx`) rehosts, rejoins or re-watches; the server re-sends the current question and reveal.
- **Server** (`server/src`): Fastify + socket.io on a single port. In production the same origin serves the built SPA (with a fallback to `index.html`), so QR join links work.
  - `rooms.ts`: an in-memory room registry plus GC. There is no database.
  - `arena.ts`: socket handlers for create, join, rejoin, rehost, watch, and leave. Identity is a client-generated `playerId`/`hostId` (the device UUID). Rejoining with the same id rebinds the socket and keeps the player's score. A disconnected host has a 90 s grace window (`HOST_GRACE_MS`) before the room closes. At the podium the host can "Play again" (`host:rematch` → `backToLobby`): same code, connected players stay, scores reset, `RoomState.game` increments; in the lobby `host:options` changes the options.
  - `game.ts`: a server-driven phase loop (`intro → reading → question → reveal → leaderboard → … → podium`) with one pending timer per room. The host can skip phases. `intro` (`INTRO_MS` 6 s, `game:intro`) opens every game: `startIntro` picks the three most experienced connected players (level, then XP, then join order; the join payload carries the profile's `xp`, clamped by `cleanXp`, and only `ArenaPlayer.level` is public), the last `INTRO_COUNTDOWN_MS` is Ready… Set… Go! on the clients; a rejoin mid-intro gets the time left. Questions go to clients **without `correctIndex`**, which is sent only in `game:reveal`. Phase durations are sent as `endsInMs` relative to receipt, so clients need no clock sync.
- **Motion** (`app/src/motion/`): the shared animation layer, built on the `motion` library (`motion/react`). Take springs, durations and effects (`shake`, `glow`, `pulse`, `popIn`) from `tokens.ts` instead of using one-off timings. The building blocks are `AnimatedNumber`, `CountdownRing` (driven by the same `endsAt` deadline as the timer digits) and canvas confetti (`fireConfetti` / `fireCannons`, which render through the `<ConfettiLayer/>` mounted in `App.tsx`). `App.tsx` animates screen changes with `AnimatePresence` and respects the OS reduce-motion setting. Never put `initial={false}` on an `AnimatePresence`: Motion keeps it for the first child's whole life, so every motion element mounted inside it later skips its enter animation. Skip only the first child's own animation with `useIsFirstKey` (one child) or `useFirstKeys` (a list) from `motion/firstKey.ts`. `/motion-lab` is a dev-only page for previewing everything. Vite dedupes `react` because `motion` is installed at the root `node_modules` while React lives in `app/node_modules`.
- **Art** (`app/src/art/`, images in `app/public/art/`): AI-painted assets made with `art-pipeline/` (see below). `Avatar`/`PaintedPortrait` render a player's look: the circle-cropped bust plus what they wear; unknown character ids fall back to David (`parseLook` in `shared/src/looks.ts`). `art/textures.ts` holds the procedural parchment and stone textures.
- **Characters and looks** (`shared/src/looks.ts`, `app/src/looks/`, economy in `docs/economy.md`): 24 characters × 3 skin tones (`char-<id>-<light|olive|dark>.webp`, 320×320, squared like the old circle crop; the tone each was first painted in is `NATURAL_TONE`). Every `avatar` field (profile, arena, board games, public views) carries a **look string** `base.tone.head.neck.frame.backdrop`; a bare old id like `david` stays valid and `cleanLook` (server: `cleanAvatar` in `rooms.ts`) turns anything into a valid look. Head/neck items are painted overlays (`item-<id>.webp`) placed by `looks/bustArt.ts` `itemPlacement` (per-character anchors in % of the bust, shared by its three tones: `head` with `brow` = the eyebrows' line, `neck` = where the neck meets the shoulders, and `cover` polygons for what hangs in front of a necklace: beards, braids, scarves, hands, straps, held props) and `ITEM_FIT` per item. Bands, coins and the circlet sit just above `brow`; wreaths span head top → temples; turbans hang from the head top; a ring's back fades out (`back`). A neck item gets an inline SVG mask: hidden above the neck line (its strands go behind the neck) and inside the covers. Measure on the dev pages `/looks-lab?grid=1&size=900` (bare busts on a 5 % grid with the anchors) and check with `/looks-lab?slot=neck&crop=45&size=310` / `?slot=head` (every character × every item, `tone=`, `chars=`, `items=`); re-measure when a bust is regenerated. Frames are SVG rings and backdrops CSS (`theme/looks.css`). Head items may rise above the circle. The picker (`LookPicker.tsx`, mounted once in `App.tsx`, `openLookPicker()`; `LookButton` in Profile and the arena / flock / spies join screens) previews anything; buying goes through `POST /api/looks/buy` (`server/src/looks.ts`), the wardrobe is `profile.wardrobe` (server-owned; sync adds earned rare items and strips unowned worn ones). Rare items unlock from `stats.arenaWins`, `stats.bestDailyStreak`, `questionsCorrect`, level and Scholar points.
- **Arena game UI** (`app/src/screens/arena/game/`, styles in `app/src/theme/empire.css`): the "Empire" look, shared with Bible Blitz (`RaceScreen` feeds the same props-driven `QuestionView` and `RoadToThrone`), with a throne room, a parchment scroll and gilded answer cards (`AnswerCard`). `ArenaGameScreen` picks a scene (`intro` / `q-N` / `lb-N` / `podium`) and transitions between scenes with `AnimatePresence`; a question keeps its key through reading → question → reveal. Players hold a fanned hand of cards and play one; it flips gold or iron at the reveal, then `PlayerResult` shows the medallion verdict. Boards (host, spectator; `eh-wide`) show four big cards with the answer distribution. The start intro is `Intro.tsx` (`ArenaIntroView`, styles in `theme/arena.css`): the top three on gold/silver/bronze medallions with their level (Rebuild the Wall: the teams at their gates), then Ready… Set… Go! timed from the phase deadline. Standings between questions go by room size (`Leaderboard.tsx`, `ROAD_MAX_PLAYERS` = 8): up to 8 players race the Road to the Throne, bigger rooms get `RankList.tsx` (Kahoot-style: top 10 on boards, top 7 plus your own row on phones, with points gained and ▲/▼; rows count up in the old order, then slide into the new one). Phones add a brief `Standing` (place, score, gaps) below either.
- **Ceremonies** (`app/src/ceremony/`): `RoadToThrone` is the standings scene between questions. Chariots race up a red carpet, so height is progress; consecutive ranks keep a minimum gap and close pairs step sideways. Chariot size (`base`) is a % of the stage's width and the tags use `cqw`, so a projector gets big chariots; boards draw the stage 1.2× anchored at the bottom (`empire.css`) so the carpet fills more of the screen. `shown` sets how many chariots are drawn (default 6, the arena passes `ROAD_MAX_PLAYERS`); a pack above six is drawn a little smaller. A player's colour comes from join order, and the leader trails fire. `Crowning` is the end-of-game ceremony for both the arena and Bible Blitz: 3rd → 2nd → 1st, each shown as their framed look portrait on a pedestal, get bronze, silver and gold crowns (placed by the bust's head anchor; the crown replaces a worn head item) in about 7 s, then the final scene stays until someone acts. God is shown only as light. Both use per-background geometry tables in % of the image. When a background is regenerated, re-measure them against a grid overlay.
- **Arena room options**: `RoomConfig.categories` and `RoomConfig.difficulty` (`easy`/`mixed`/`hard`) filter `server/src/bank.ts`. The server also remembers the question ids each `hostId` has played, so back-to-back games avoid repeats.
- **Coins** (`shared/src/coins.ts`): the single table of rewards per mode (`arena` > `blitz` > `practice`; the Daily Scroll pays the arena rate). Open Arena also awards XP (= points scored) at the podium, like Bible Blitz. Coins and XP from Bible Blitz and the arena are credited to the saved profile **only when the game finishes**, so leaving forfeits them. The arena server keeps each player's total (`LeaderboardEntry.coins`) and the app pays it at `game:podium`, once per game (`sixtysix.arenaPaid.v1`, keyed `CODE#game`). Practice and the Daily Scroll pay per answer. Board games pay once per finished game (`BOARD_REWARDS`; both by win/loss), credited client-side when the final/over state arrives (`app/src/game/boardRewards.ts`, `sixtysix.boardPaid.v1`). Coins buy Jerusalem materials and look items; `docs/economy.md` has the concept.
- **Practice** (`app/src/practice/practiceStore.ts`, `screens/practice/`): untimed solo mode. It loads the bank and `verses.json` lazily. Missed question ids are saved in `localStorage` (`sixtysix.practiceMissed.v1`); they return later in the session and feed "Review my mistakes".
- **My Home in Jerusalem** (`docs/jerusalem-plot.md`): an optional building layer for signed-in players.
  - `shared/src/plot.ts` holds every building, level, cost, build time, requirement, water and storehouse value and the Market prices, ported 1:1 from `docs/balance/plotsim.py` (change both together). It also has the rules: `checkUpgrade`, `advance` (finishes builds and adds production lazily from timestamps, capped by the storehouse), `collect` and `suggestNext`.
  - `server/src/plot.ts` is the authority. It stores one JSON `PlotState` per user in the `plots` table (created in `accounts.ts`). All spending happens there: `GET /api/plot` (creates the plot with the starter gift), `POST /api/plot/buy|sell|upgrade|collect`, and the Workers' scroll (`POST /api/plot/scroll`, then `/scroll/answer`: 2 of 3 right takes 5 minutes off a build). Each response returns `coins`; the app adopts them (`plot/plotStore.ts`, which syncs first if grants are still queued).
  - Screens: `screens/home/HomeScreen.tsx` (header, next step, the plot scene, building sheet, scroll) and `MarketScreen.tsx`; the `home` and `market` screens return to `lastTab`. Painted building art (`app/public/art/plot-*.webp`, a few stages per building, mapped per level in `screens/home/homeUtil.ts`) is used in sheets, the next step and the list fallback, not in the scene.
  - **Explorable world** (`app/src/world/`, styles in `theme/world.css`): `PanZoom` is the shared drag/pinch/wheel window (clamped from "whole world fits" to `maxZoom`; children in world px; `useWasDragged` from `dragged.ts` stops the click that ends a drag). `CityMap` is the painted 2D city (the fallback, see below): `city-map.webp` (with `PAD` world px of blurred surround so edge lots show in full; map coordinates stay in painting px inside `.cm-world`), landmark sprites (`land-*.webp`), search, townsfolk (`CityLife`: 8–36 people by the number of families and how many were active today, plus a few animals, walking the road graph `ROADS`/`LINKS` (in % of the painting) between houses, landmarks and gates), and one lot per resident; its search box and found-family card are `CityChrome.tsx`, shared with the 3D city. `cityLayout.ts` holds the geometry in % of the painting (re-measure with a grid overlay if it is regenerated); plot n always gets `LOTS[n-1]` (free cells sorted by distance from `TEMPLE`, inside the wall first; `TEMPLE` is only that anchor and must not move, since `users.lot` is stored; the Temple sprite has its own place in `LANDMARKS`, centred on the painted platform). Lots are culled to the visible area, and names show only when zoomed in.
  - **3D city** (`app/src/world/city3d/`, styles `theme/city3d.css`; three.js + `@react-three/fiber` 9 + `@react-three/drei`): the Jerusalem tab. `world/CityView.tsx` lazy-loads `city3d/City3D.tsx` as its own chunk (three.js never reaches the main bundle) and falls back to `CityMap` without WebGL, if the chunk fails, or on `webglcontextlost`; `localStorage['sixtysix.city2d.v1'] = '1'` forces 2D. `space.ts` maps painting px to units (1 unit = 10 px, centred; x east, y up, z south, so the default view looks north like the painting) and is the one height function (`heightAt`: plateau rising west, Moriah, the Kidron/Hinnom falling away outside the wall, the Mount of Olives; `surfaceAt` adds the platform `MOUNT_PTS`/`MOUNT_TOP` and its four `STAIRS`). **`plan.ts` is the layout** (three-free, units): the Temple Mount is the rectangle `MOUNT_RECT` (shared, px) square to the wall, with a paved plaza ring (`PLAZA`, walkers' ring `RING`) and stairs mid-side; `SANCTUARY`/`ANTONIA` place and scale Herod's Temple and the fortress; `LANDMARK_RECTS` (market, governor, pool) and `PEN` stand in lot-free space; four `MAIN_ROADS` run from the plaza through the `GATES` (where they cross the wall; the east one is the Sheep Gate) to the map edge; `WALL_SEGS`/`TOWER_AT`/`wallRects()` are the wall. Houses are drawn at `HOUSE_SCALE` (0.75; My Home stays life-size) so a lot's yard (`LOT_HALF` round `lotCentre`, house turns are quarter turns only) leaves room for streets. `streets.ts` builds the street network from the plan and the lot grid: main roads + plaza ring, a street between every two rows of lots, alleys through every other gap, the walkers' graph (`CITY_NET`, a `StreetNet` for `townsfolk(homes, net)`; the 2D map keeps `PAINTED`, the roads on the painting); `roads.ts` paves them (draped strips, kerbs on main roads); `PoolWater.tsx` is the Pool's water (tinted, two drifting ripple layers, a few frames a second only while near and on screen, still under reduced motion); `view.ts` `clearView` turns/tilts a fly-to so the Mount, a landmark or the wall doesn't hide the target. **Nothing may stand on a lot:** `node app/scripts/city-layout-check.mts [--near]` (via `npx tsx`) tests every open lot against the plan's footprints, the streets, the trees and the built triangles, checks the `LOTS` hash and lists the next lots new families get; run it after any layout change. The camera keeps its last view for the session (back from Visit). Everything is procedural, no image files: `geo.ts` bakes boxes/prisms/cylinders with vertex colours and box-projected UVs into merged geometries; `buildings.ts` builds the static city as two meshes (stone, plaster): the wall along the `WALL` ellipse with merlons, towers and real gate passages, the Temple Mount (porticoes, Royal Stoa south, Solomon's Porch east, Antonia in the north-west corner) with Herod's Temple facing east, the paving (`roads.ts`), the market, governor's palace, Pool of Siloam and sheep pen where `plan.ts` puts them (the 2D map's `LANDMARKS` sprites stay where they are painted); `houses.ts` puts the shared house models (`models.ts`, below) on a foundation, instanced per level (one draw call each), plus each family's fence ring by wall level (`fence.ts` `lotFenceGeometries`, one instanced mesh per level; `/api/city` sends `wall` beside `house`), free plots, weeds (20/40 days) and "For sale" boards (text painted in the player's language, `textures.ts`); `terrain.ts` paints the ground texture (a worn edge under the streets, a pale yard under every open lot); `trees.ts` instances olives and cypresses whose crowns stay off yards, streets, the plaza, the wall and landmarks. A house stands at `lotCentre(LOTS[n-1])` (a little north of the 2D foot point). `CityScene.tsx` (inside the Canvas) holds lights, static shadows (drawn once, again only when houses change), fog that follows the zoom, the camera rig and the per-frame work for the HTML on top; `bridge.ts` is the mutable object the scene and the HTML share (controls, pick functions, label elements, compass, `invalidate`). Camera: camera-controls via drei, set up by `rig.ts` (`configureRig`, also the tap/twist pointer hook `useScenePointer`, `labelAt`, `maxDpr`, `useContextLost`; the buttons are `NavButtons.tsx`), shared with My Home; phone: one finger pans, two pinch/twist/tilt; mouse: left turns, right pans, wheel zooms; buttons turn ±45°, zoom, and the compass sets north up; tilt, distance and pan are clamped (`MIN_DIST`…`MAX_DIST`, polar 0.12–1.18). The canvas renders on demand: anything that moves the camera from code must call `bridge.invalidate()`. Taps (`City3D`: a press that moves < 9 px): name labels first (HTML, `pointer-events: none`, placed every frame and mounted only near and on screen, except landmarks, my home, the found family and the first free lots, which carry `data-tour` and `data-lot`; the wrapper is a `.pz` so the tour's `PZ_REVEAL` flies to them), then walkers, then a ray against invisible per-lot boxes and landmark boxes: a house flies there and shows the found card (Visit / Build), free and for-sale lots open `CitySheet`, landmarks their card. Reduced motion: fly-tos jump, walkers stand still. Dev only: `window.__city3d` (the bridge) and `window.__city3dGl` (the renderer) for tests.
  - **My Home in 3D** (the only drawing of the homestead: the painted yard and the painted valley were removed on the owner's request, with their code and paintings; `HomeScreen` has two tabs, Homestead and Expeditions): the six fields and the threshing floor lie outside the fence (`city3d/fields3d.ts` `FIELD_3D` / `THRESH_3D`, beds per field level, crops as two instanced meshes fed by a `crops` string, the season strip and Harvest all under the scene); the scene has the city's sky dome, `daylight.ts` period, `quality.ts` tier, ground grain, a contact shade under every building and bed, lamps at dusk and night, `YARD_PROPS` things standing about by house level, and CSS cloud shadows and birds on top that cost no frames (`city3d/Plot3D.tsx` HTML side, `city3d/PlotScene3D.tsx` inside the Canvas, `city3d/plotSpace.ts` layout; styles at the end of `theme/city3d.css`). `world/PlotView.tsx` (props in `world/plotProps.ts`; used by My Home with taps and by the `visit` screen, `VisitScreen.tsx`, `visitPlot(username)`, read-only) lazy-loads `Plot3D` (its own small chunk; three.js, drei, fiber, `geo.ts`, `models.ts` etc. land in one shared chunk with the city, so nothing downloads twice). If the GPU drops the context the scene is mounted afresh (twice at most); without WebGL, or if the chunk fails or throws (`Fallback3D.tsx`), `world/PlotList.tsx` shows the buildings as a plain tappable list. `rig.ts` `useContextLost` ignores the `webglcontextlost` that R3F itself causes when a canvas unmounts (the canvas has left the page): treating that as a loss once switched the home to its fallback whenever the Expeditions tab was opened. Who lives in the yard comes from `world/yard.ts` (`specsFor` by building level, the path graph `YARD_EDGES`; `useYardActors` adds the gift signs: carriers with a gift waiting wear a material sign and a tap calls `POST /api/plot/gift`, rules in `shared/src/life.ts`: once per carrier every 3 h, 6 a day, own plot only). **One set of building models for both scenes:** `models.ts` `buildingGeometry(spot, level)` (cached; level 0 = a pegged-out site; house 1–7 via `drawHouse`, also what the city's houses are made of; well, storehouse, workshop, sheepfold, olive grove, brick kiln, the gate at the `wall` spot, the Bakehouse (a paved courtyard until it is built), the Stable with its donkeys and camels), `threshGeometry`, `sheepGeometry`, the `PROP` catalogue, `scaffoldGeometry` (poles, planks, ladder, stone heap; sized to what is going up) and `FOOTPRINT` per spot; every model stands on y = 0 facing +z in city units (a person ≈ 2.2). The yard (`plotSpace.ts`) is a diamond, half-diagonal `R` = 31, the gate filling a gap (`GATE_HALF`) at the south corner; `SPOT_3D` places and turns the nine spots, `YARD_3D` lays the same path graph out round them (walker px = units × `PX` 20), `FENCE_PATHS`/`TOWER` for the fence, a flat yard rising into low hills (`groundAt`), a ground texture painted at load (earth, worn paths, two flagstone paths crossing in front of the house, the lane out of the gate) and olive trees round it. `fence.ts` `fenceParts` lays the wall level's pieces (stakes, hedge bushes, posts and rails, stone wall, high wall with merlons, watchtower); the yard draws them instanced, one mesh per kind. A build in progress shows scaffolding and the tag's progress bar and countdown; when a level goes up the model springs up out of dust with a gold ring (skipped with reduced motion).   - **The city's light and shade** (`docs/graphics-plan.md`): the city canvas uses ACES tone mapping at `EXPOSURE` (`bridge.ts`); a warm sun against cool sky light. `sky.ts` is the sky dome (static, no time uniform; its `haze` must equal the fog colour, `HAZE` in `CityScene.tsx`) and `farHills` (a ring of hills past the terrain's edge, so the square never shows). `ao.ts` `bakeAo` bakes ambient shade into vertex colours, once per geometry (a second call darkens again): house, building and fence models through `Geo.build(uv, { ao })` (`ground: () => 0`, or −3 for models on a foundation), the static city in `CityScene` shortly after the first frame (it costs more than building the city). ## Deployment

See `docs/deploy.md`. The app build ends with `scripts/precompress.mjs` (`.br` / `.gz` next to each file; `SKIP_PRECOMPRESS=1` skips it, e.g. before `npx cap sync`); the server serves those and sets the cache headers (`cacheControlFor` in `server/src/index.ts`), so it never compresses. `app/public/sw.js` is the service worker (production web builds only): pages network-first, `/assets/` cache-first, art stale-while-revalidate, never `/api` or `/socket.io`. Live on Cloudflare at 66.gracelabs.dev (one Durable Object, `cloudflare/`, `wrangler.jsonc`, `docs/cloudflare-migration.md`): every push to `main` deploys via Cloudflare Workers Builds (settings in `docs/deploy.md`); `dev` never deploys. On Cloudflare the files are served by static assets with `_headers` (`cloudflare/write-headers.mjs`), not by the server. The old Node setup (`Dockerfile`, `fly.toml`) still works: exactly one instance, persistent volume at `/data`.
