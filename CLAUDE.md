# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**66** is a Bible-quiz game (named for the 66 books of the Bible). It has two modes:
- **Bible Blitz**: a solo chariot race against bots. It runs entirely on the client and works offline.
- **Open Arena**: a Kahoot-style hosted multiplayer game. The server holds the authoritative state, players join by room code or QR, and a spectator board is available.

`PLAN.md` (gitignored, local only) holds the product/architecture plan. Code comments refer to its sections, e.g. "PLAN.md §6".

## Commands

This is an npm workspaces monorepo (`app`, `server`, `shared`). Run commands from the repo root:

```bash
npm install
npm run dev:app        # Vite dev server; proxies /socket.io and /api to :3066
npm run dev:server     # arena server (tsx watch) on :3066 (PORT env overrides)
npm run build          # app: tsc -b && vite build → app/dist
npm run start          # server; also serves app/dist if it exists
npm run lan            # build app + start server → play over wifi via printed LAN URL / QR

npm run lint --workspace app
npm run typecheck --workspace server
npm run i18n:check --workspace app   # translations complete (docs/i18n.md)
```

There is no test suite. The checks are type-checking (`npm run build` for the app, `typecheck` for the server) and lint.

Native shells: Capacitor (`app/ios`, `app/android`, `webDir: dist`). After a build, sync with `npx cap sync` from `app/`.

Art pipeline (run from `art-pipeline/`, which has its own `npm install` for `sharp`; see its README). Generates images with Google's Nano Banana model. The key goes in the gitignored `art-pipeline/.env.local`. Calls are paid (about $0.03 per image), so use `--dry-run` first:
```bash
node generate.mjs --dry-run                 # print the prompts from prompts.json, no API calls
node generate.mjs --only=<asset> --count=3  # candidates → out/ (raw originals kept in out/raw/)
node contact-sheet.mjs <prefix>             # side-by-side review sheets → out/_sheet-*.png
```
Copy the chosen images into `app/public/art/` as trimmed WebP.

Question pipeline (plain Node scripts, run from `question-pipeline/`; see its README for batch format and rules):
```bash
node scripts/fetch-bible.mjs   # once: WEB Bible corpus → data/web-bible.json
node scripts/verify.mjs        # data/generated/*.json → verified / review-queue / rejected
node scripts/review.mjs        # interactive: approve/reject review-queue items (a/r/s/q)
node scripts/compile.mjs       # verified + approved-manual → app/src/questions/bank.json + verses.json
```

## Architecture

- **`shared/`** (`@sixtysix/shared`) is TypeScript source with no build step. Vite resolves it through the workspace, and the server resolves it through a tsconfig `paths` entry and runs it with `tsx`. It contains:
  - `protocol.ts`: the socket.io event maps (`ClientToServerEvents` / `ServerToClientEvents`), `RoomState`, and `ArenaPhase`. **Any change to arena messaging starts here.**
  - `scoring.ts`: `scoreAnswer` (500 base + up to 500 speed bonus over `QUESTION_TIME_MS`). The app (`app/src/game/scoring.ts` re-exports it) and the server use it, so both compute scores identically.
  - `question.ts`: the `Question` type.
- **Question bank**: `app/src/questions/bank.json` (about 1,500 questions) and `verses.json` (the cited verse text for each question id) are generated by `question-pipeline/compile.mjs`, so don't edit them by hand. The app loads the bank lazily as its own chunk; the server sends the verse text in `game:reveal`. The app bundles it through `questions/provider.ts` (the `QuestionProvider` abstraction). The server reads the same file from disk in `server/src/bank.ts`.
- **App** (`app/src`): React 19 + Zustand. There is no router. `App.tsx` maps the `screen` value in `game/store.ts` to a component, and you navigate with `useGameStore.getState().goTo(screen)`. `main.tsx` parses the deep links `/join/CODE` (prefills the arena join flow) and `/board/CODE` (spectator), then resets the URL to `/`.
  - `game/store.ts`: the Bible Blitz race state machine (reading → question → reveal → progress → podium) with local timers, bots (`bots.ts`), and the player profile. Persistence in `persistence.ts` uses versioned `localStorage` keys (`sixtysix.*.v1`), including the stable device UUID that serves as arena identity.
  - `arena/arenaStore.ts`: the socket.io client and all live arena state. Its role is `host | player | spectator`. Host and spectator views get the wide layout (`app-wide`) because they are meant for projectors. A reload lands back in the game: the room and role are kept in `sixtysix.arenaSession.v1` (6 h) and `resume()` (called from `main.tsx`) rehosts, rejoins or re-watches; the server re-sends the current question and reveal.
- **Server** (`server/src`): Fastify + socket.io on a single port. In production the same origin serves the built SPA (with a fallback to `index.html`), so QR join links work.
  - `rooms.ts`: an in-memory room registry plus GC. There is no database.
  - `arena.ts`: socket handlers for create, join, rejoin, rehost, watch, and leave. Identity is a client-generated `playerId`/`hostId` (the device UUID). Rejoining with the same id rebinds the socket and keeps the player's score. A disconnected host has a 90 s grace window (`HOST_GRACE_MS`) before the room closes.
  - `game.ts`: a server-driven phase loop (`reading → question → reveal → leaderboard → … → podium`) with one pending timer per room. The host can skip phases. Questions go to clients **without `correctIndex`**, which is sent only in `game:reveal`. Phase durations are sent as `endsInMs` relative to receipt, so clients need no clock sync.
- **Motion** (`app/src/motion/`): the shared animation layer, built on the `motion` library (`motion/react`). Take springs, durations and effects (`shake`, `glow`, `pulse`, `popIn`) from `tokens.ts` instead of using one-off timings. The building blocks are `AnimatedNumber`, `CountdownRing` (driven by the same `endsAt` deadline as the timer digits) and canvas confetti (`fireConfetti` / `fireCannons`, which render through the `<ConfettiLayer/>` mounted in `App.tsx`). `App.tsx` animates screen changes with `AnimatePresence` and respects the OS reduce-motion setting. `/motion-lab` is a dev-only page for previewing everything. Vite dedupes `react` because `motion` is installed at the root `node_modules` while React lives in `app/node_modules`.
- **Art** (`app/src/art/`, images in `app/public/art/`): AI-painted assets made with `art-pipeline/` (see below). `Avatar`/`PaintedPortrait` render a player's look: the circle-cropped bust plus what they wear; unknown character ids fall back to David (`art/characters.ts`). `art/textures.ts` holds the procedural parchment and stone textures.
- **Characters and looks** (`shared/src/looks.ts`, `app/src/looks/`, economy in `docs/economy.md`): 24 characters × 3 skin tones (`char-<id>-<light|olive|dark>.webp`, 320×320, squared like the old circle crop; the tone each was first painted in is `NATURAL_TONE`). Every `avatar` field (profile, arena, board games, public views) carries a **look string** `base.tone.head.neck.frame.backdrop`; a bare old id like `david` stays valid and `cleanLook` (server: `cleanAvatar` in `rooms.ts`) turns anything into a valid look. Head/neck items are painted overlays (`item-<id>.webp`) placed by `looks/bustArt.ts` (per-character head and neck anchors in % of the bust, shared by its three tones, measured against `node looks.mjs grid …` in art-pipeline; re-measure when a bust is regenerated) and `ITEM_FIT` per item; frames are SVG rings and backdrops CSS (`theme/looks.css`). Head items may rise above the circle. The picker (`LookPicker.tsx`, mounted once in `App.tsx`, `openLookPicker()`; `LookButton` in Profile and the arena / flock / spies join screens) previews anything; buying goes through `POST /api/looks/buy` (`server/src/looks.ts`), the wardrobe is `profile.wardrobe` (server-owned; sync adds earned rare items and strips unowned worn ones). Rare items unlock from `stats.arenaWins`, `stats.bestDailyStreak`, `questionsCorrect`, level and Scholar points.
- **Arena game UI** (`app/src/screens/arena/game/`, styles in `app/src/theme/empire.css`): the "Empire" look, shared with Bible Blitz (`RaceScreen` feeds the same props-driven `QuestionView` and `RoadToThrone`), with a throne room, a parchment scroll and gilded answer cards (`AnswerCard`). `ArenaGameScreen` picks a scene (`q-N` / `lb-N` / `podium`) and transitions between scenes with `AnimatePresence`; a question keeps its key through reading → question → reveal. Players hold a fanned hand of cards and play one; it flips gold or iron at the reveal, then `PlayerResult` shows the medallion verdict. Boards (host, spectator; `eh-wide`) show four big cards with the answer distribution.
- **Ceremonies** (`app/src/ceremony/`): `RoadToThrone` is the standings scene between questions. Chariots race up a red carpet, so height is progress; consecutive ranks keep a minimum gap and close pairs step sideways. A player's colour comes from join order, and the leader trails fire. `Crowning` is the end-of-game ceremony for both the arena and Bible Blitz: 3rd → 2nd → 1st, each shown as their framed look portrait on a pedestal, get bronze, silver and gold crowns (placed by the bust's head anchor; the crown replaces a worn head item) in about 7 s, then the final scene stays until someone acts. God is shown only as light. Both use per-background geometry tables in % of the image. When a background is regenerated, re-measure them against a grid overlay.
- **Arena room options**: `RoomConfig.categories` and `RoomConfig.difficulty` (`easy`/`mixed`/`hard`) filter `server/src/bank.ts`. The server also remembers the question ids each `hostId` has played, so back-to-back games avoid repeats.
- **Coins** (`shared/src/coins.ts`): the single table of rewards per mode (`arena` > `blitz` > `practice`; the Daily Scroll pays the arena rate). Open Arena also awards XP (= points scored) at the podium, like Bible Blitz. Coins and XP from Bible Blitz and the arena are credited to the saved profile **only when the game finishes**, so leaving forfeits them. The arena server keeps each player's total (`LeaderboardEntry.coins`) and the app pays it at `game:podium`, once per room (`sixtysix.arenaPaid.v1`). Practice and the Daily Scroll pay per answer. Board games pay once per finished game (`BOARD_REWARDS`; both by win/loss), credited client-side when the final/over state arrives (`app/src/game/boardRewards.ts`, `sixtysix.boardPaid.v1`). Coins buy Jerusalem materials and look items; `docs/economy.md` has the concept.
- **Practice** (`app/src/practice/practiceStore.ts`, `screens/practice/`): untimed solo mode. It loads the bank and `verses.json` lazily. Missed question ids are saved in `localStorage` (`sixtysix.practiceMissed.v1`); they return later in the session and feed "Review my mistakes".
- **My Home in Jerusalem** (`docs/jerusalem-plot.md`): an optional building layer for signed-in players.
  - `shared/src/plot.ts` holds every building, level, cost, build time, requirement, water and storehouse value and the Market prices, ported 1:1 from `docs/balance/plotsim.py` (change both together). It also has the rules: `checkUpgrade`, `advance` (finishes builds and adds production lazily from timestamps, capped by the storehouse), `collect` and `suggestNext`.
  - `server/src/plot.ts` is the authority. It stores one JSON `PlotState` per user in the `plots` table (created in `accounts.ts`). All spending happens there: `GET /api/plot` (creates the plot with the starter gift), `POST /api/plot/buy|sell|upgrade|collect`, and the Workers' scroll (`POST /api/plot/scroll`, then `/scroll/answer`: 2 of 3 right takes 5 minutes off a build). Each response returns `coins`; the app adopts them (`plot/plotStore.ts`, which syncs first if grants are still queued).
  - Screens: `screens/home/HomeScreen.tsx` (header, next step, the plot scene, building sheet, scroll) and `MarketScreen.tsx`; the `home` and `market` screens return to `lastTab`. Painted building art is `app/public/art/plot-*.webp`, a few stages per building, mapped per level in `screens/home/homeUtil.ts`.
  - **Explorable world** (`app/src/world/`, styles in `theme/world.css`): `PanZoom` is the shared drag/pinch/wheel window (clamped from "whole world fits" to `maxZoom`; children in world px; `useWasDragged` from `dragged.ts` stops the click that ends a drag). `PlotScene` draws a homestead on `plot-ground.webp` with the nine sprites at fixed % positions, a fence ring drawn in SVG along the painted yard edge for each wall level (corner stakes, hedge, wooden fence, stone wall, wall with merlons, watchtower; the front sides sit above the sprites, name tags on a layer above that) and `PlotLife` (figures `life-*.webp` that appear with building levels: children and hens, the flock, craftsmen, a water carrier, a pack donkey, a watchman; CSS-animated, still for reduced motion); My Home uses it with taps, the `visit` screen (`VisitScreen.tsx`, `visitPlot(username)`) read-only for someone else's plot. `CityMap` is the Jerusalem tab: `city-map.webp` (with `PAD` world px of blurred surround so edge lots show in full; map coordinates stay in painting px inside `.cm-world`), landmark sprites (`land-*.webp`), search, townsfolk (`CityLife`: 8–36 figures by the number of families and how many were active today, walking door to door, to landmarks and out of town as CSS offset-path trips), and one lot per resident. `cityLayout.ts` holds the geometry in % of the painting (re-measure with a grid overlay if it is regenerated); plot n always gets `LOTS[n-1]` (free cells sorted by distance from the Temple, inside the wall first). Lots are culled to the visible area, and names show only when zoomed in.
  - **Lots and activity** (`docs/jerusalem-growth.md`, rules in `shared/src/city.ts`): each account has a stored lot (`users.lot`, 1…413, lots 1–103 inside the wall; the geometry is `shared/src/cityLayout.ts`, re-exported by `app/src/world/cityLayout.ts`). New families take the first free lot, inner first. `markActive` (sign-in, syncs that apply rewards, plot actions) sets `users.last_active`; the map shows weeds at 20/40 days and "For sale" after 60 (My Home warns via `home` in the plot API). `POST /api/city/move` (`server/src/city.ts`) moves a homestead to a free lot or takes over one idle 60+ days (500 / 1,000 coins; inside the wall a Courtyard house is needed). Migrations in `accounts.ts` check each column, so a half-finished upgrade completes on the next start.
  - `/api/city` (residents with `lot`, `idleDays`, `house`) and `/api/players/:username` include house and building levels.
  - For a second dev stack, `API_TARGET=http://localhost:3167 npx vite --port 5274` points the Vite proxy at another server.
- **Arena identity**: the device UUID (`getDeviceId`) is a **secret** sent only on join/rehost. The server gives each player a random public id, and that is the only id broadcast. The client compares against `useArenaStore.myPlayerId`, never against the device id. Socket handlers are wrapped in a try/catch and validate every payload, so a malformed message must never crash the server.
- **Board games: Wolf in the Flock** (`docs/board-games.md` has the research and rules): a hidden-role party game (3–12 players, each on a phone, optional shared board). One game = one secret Bible word. Everyone sees it except the wolf (two wolves from 7 players), who sees only the category. Players give short clues in a random order (an opening wolf sees the word's hand-written `wolfHint`); after each lap the flock decides to vote or play another lap (lap 4 forces the vote). A wolf types (and may change) a guess of the word until a vote starts; then it locks. Each player has one vote per wolf still hiding. Voting out a sheep → wolves win; a caught wolf whose locked guess is the word (`flock/match.ts`: typos and `aliases` count, close calls go to a sheep vote) wins; otherwise that wolf has lost (`result.lostIds`) and the flock wins once no wolf is left. It is fully separate from the arena: protocol in `shared/src/flock.ts` (`flock:*` events), server in `server/src/flock/` (own room registry + GC, socket channel `flock:CODE`; the curated word list with aliases is `shared/src/flockWords.json`, shared with the one-phone mode), client in `app/src/flock/flockStore.ts` (own socket) and `app/src/screens/flock/` (one `flock` screen; the phase picks the view), styles in `app/src/theme/flock.css`. Public `FlockState` never contains the word or the wolves before phase `over` (phase `out` reveals only the player just voted out); each card goes privately via `flock:secret`. Deep links: `/flock/CODE` (join) and `/flock/CODE/board` (board, wide layout). **One phone mode** (`flockLocal` screen, `app/src/flock/local/` + `screens/flock/local/`): Splash-style pass-and-peek on one device, fully client-side (no server, no word checks, no rewards); setup saved in `sixtysix.flockLocal.v1`. The same device-id identity rules as the arena apply, and the last room code is kept in `localStorage` (`sixtysix.flockRoom.v1`) for "Back to game" after a reload. **Bots** (`server/src/flock/bots.ts`; leader-only `flock:addBot` / `removeBot` / `botLevel` in the lobby): a bot is a seat with `bot: true` and no socket that plays through the same `act*` functions as the socket handlers, planned after every broadcast; sheep clue from each word's `clues` in `flockWords.json`, a wolf guesses by matching the clues against every word of the category. Games pay rewards only with 3+ people dealt in (`FlockResult.rewarded`). **Mixed languages:** each seat has a `locale` (sent with create/join, `flock:locale` after a switch; bots use the leader's). One entry is dealt (category + index into `flockWords.json` and the same-order `flockWords.de.json` / `.hu.json`); cards come in each player's language, `FlockResult.words` holds every language, and clue/guess checks cover every language seated (`roomLocales` / `wordIn` in `flock/rooms.ts`; ß, German/Hungarian filler and Hungarian case endings in `match.ts`, which takes the room's languages and behaves as before for English only). The one-phone mode deals from the app language's list.
- **Board games: Twelve Spies** (Bible Codenames, Numbers 13; rules in `docs/board-games.md`): two tribes (Judah gold, Ephraim blue; co-op from 2 players) find their words on a 5×5 grid from their spy master's one-word clues. It mirrors the flock's architecture and is just as separate: protocol in `shared/src/spies.ts` (`spies:*` events), server in `server/src/spies/` (own registry + GC, channel `spies:CODE`, its own `words.json` of short words; `dealWords` never deals two words where one contains the other, and `clashesWithGrid` refuses clues that are, contain or are part of a visible word), client in `app/src/spies/` (`spiesStore.ts`, own socket) and `app/src/screens/spies/` (one `spies` screen), styles in `app/src/theme/spies.css`. **The key is the secret:** public `SpiesState` carries only revealed colours; the key goes in `spies:key` to the two spy masters only, and becomes public in `result.key` once the phase is `over`. Agents propose a card (`spies:pick`); a majority of the tribe's connected agents reveals it, or the proposer alone after `SPIES_FORCE_MS` (`spies:confirm`). An offline spy master gets 20 s before a teammate is promoted (at once if they leave); spy masters rotate on "Play again" (least served first). Deep links `/spies/CODE` and `/spies/CODE/board`; last code in `sixtysix.spiesRoom.v1`. **Mixed languages:** seats carry a `locale` (`spies:locale` after a switch); cards are dealt by English word and carry `words` in every language (`words.<lang>.json`; the client shows its own via `cardWord` in `spies/util.ts`); `dealWords` and `clashesWithGrid` check containment in every language seated. Word lists are checked with `npx tsx scripts/check-words-i18n.mts de|hu`. The Board games tab card styles (`.bg-feature`) live in `empire.css` because the games' CSS loads lazily.

- **Question flags** (`shared/src/flags.ts`, server `server/src/flags.ts`, app `app/src/flags/`): anyone (guests too) flags a question from the shared `FlagSheet` (reason chips + optional comment ≤ 500): the Bible Blitz podium review, Practice and the Daily Scroll after answering (under the verse), and the arena *player* view during the reveal (`RevealPayload.questionId`; the sheet is mounted once in `App.tsx` so the game goes on behind it). `POST /api/flags` stores a row in `question_flags` (what the player saw, locale, user id or none, a hash of the IP for the limit of 20 per day, and `content_hash` of the bank entry); the same sender flagging again updates their open flag. A question with an `open` or `confirmed` flag is **out of play**: `pickQuestions` skips it (arena, Workers' scroll), and the app fetches `GET /api/flags/excluded` (cached in `sixtysix.flagsExcluded.v1`) when it loads the bank, adds its own flags, and Bible Blitz (`BundledBankProvider`), Practice and the Daily Scroll skip them (the Daily Scroll keeps a started day's ids in its saved state). Unsent flags wait in `sixtysix.flagQueue.v1` (sent at start / next flag). On server start, flags whose question changed in the bank (hash differs) or left it become `fixed` (back in play). Review: the full-screen `review` screen (`screens/review/`, linked from Profile for staff): one tab per kind of work (`SECTIONS` in `ReviewScreen.tsx`; flags now, submitted questions later), `GET /api/admin/flags?status=open|confirmed|all`, `POST /api/admin/flags/resolve { questionId, action: 'dismiss'|'confirm', note }`, `GET /api/admin/flags/export?status=confirmed` (fix workflow in `question-pipeline/README.md`).
- **Staff roles** (`server/src/roles.ts`, `StaffRole` / `hasRole` in `shared/src/account.ts`): `admin` = a username in `ADMIN_USERNAMES` (env only, never revoked in-app); `reviewer` = `users.role`, granted / revoked by admins (`GET|POST /api/admin/reviewers`, the review screen's Reviewers tab). `Account.role` tells the app. Guard staff routes with `staffRoute(app, method, path, 'reviewer' | 'admin', fn)` / `requireRole(req, reply, need)`; an admin holds every role.
- **Google and Apple sign-in** (`server/src/google.ts`, `server/src/apple.ts`, buttons in `app/src/account/SocialSignIn.tsx`): each is enabled by an env var (`GOOGLE_CLIENT_ID`, `APPLE_SERVICES_ID`) that `/api/server-info` exposes to the app. Google ID tokens are checked with Google's tokeninfo endpoint; Apple ID tokens are verified locally (RS256 against Apple's published keys, audience = Services ID, plus `APPLE_EXTRA_AUDIENCES`). Accounts are linked by `users.google_sub` / `users.apple_sub`. Setup steps are in `docs/deploy.md`.
- **Languages** (`docs/i18n.md`): English, German, Hungarian. Questions carry every language (`questionIn`); verses per language in `verses.<lang>.json` (`question-pipeline/scripts/compile-i18n.mjs`). `app/src/i18n/index.ts` (`useT()` in components, `t()` elsewhere, `tServer()` for the server's English messages); messages per area in `app/src/i18n/<locale>/<namespace>.ts`, picked up automatically; English bundled, others lazy. Never hard-code user-facing text; `npm run i18n:check --workspace app` must pass. Language picker in Profile (`sixtysix.locale.v1`).
- **Navigation shell**: the screens in `TAB_SCREENS` (`menu` = Quiz, `boardGames`, `jerusalem`, `leaderboard`) get the shared `TopBar` (coins on the left; your portrait on the right opens Profile) and the bottom `TabBar` (`screens/shell/`). Every other screen is full-screen and brings its own back/leave button. Profile and the `player` page return to `lastTab`.
- **Public views** (`registerPublicRoutes` in `server/src/accounts.ts`, `registerCityRoutes` in `server/src/city.ts`, client `account/publicApi.ts`): `/api/leaderboard?period=week|all` (weekly = grants' XP since Monday 00:00 UTC), `/api/city` (residents and their lots) and `/api/players/:username`. Guests can view all of them; only account holders appear in them.
- **Arena modes** (`RoomConfig.mode`): `classic`, `goliath` (the room's points are damage against one giant; the game ends early when he falls) and `wall` (players split into gate teams; a team's wall height is its *average* score). Server logic is in `server/src/modes.ts`. Mode state (`RoomState.goliath` / `teams`) is part of the broadcast room state. The scenes are `app/src/ceremony/Goliath.tsx` and `Wall.tsx`. Finishing coins are added on the server per mode (`finalBonus`) and are included in `LeaderboardEntry.coins` at the podium.
- **Accounts (optional)**: username + password, using REST under `/api/account` (`server/src/accounts.ts`). The data is SQLite through Node's built-in `node:sqlite`, stored in `DATA_DIR` (default `./data` in dev, `/data` in Docker; it must be a persistent volume). Bearer tokens are stored hashed.
  - Guests keep everything on the device.
  - Signed in, every reward is queued as an idempotent `Grant` (`app/src/account/outbox.ts`) and synced. The server's totals then replace the local ones (`useGameStore.adoptProgress`).
  - Sign-up uploads the guest progress; signing in adds guest progress to the account; signing out resets the device to a fresh guest.
  - The skill tree and the Jerusalem plot (`docs/skill-tree.md`, `docs/jerusalem-plot.md`) are for signed-in players only.
- **Levels and the skill tree ("Gifts")** (`docs/skill-tree.md`, balance in `docs/balance/levelsim.py`):
  - `shared/src/skills.ts` has the level curve (`levelForXp`, `xpToReach`, `levelProgress`; `app/src/game/persistence.ts` re-exports `levelForXp`), the 23 skills in three paths (Scholar / Builder / Steward), the tier rules (`TIER_NEEDS`), `learnError`, and the effects: `xpBonus` / `coinBonus`, `plotMods` → `PlotMods`, and `giftLoadout` for quiz gifts. Change the curve here and in `levelsim.py` together.
  - The state is `profile.skills` (`SkillState`: ranks, re-specs used, weekly-perk weeks), owned by the server. `server/src/skills.ts`: `POST /api/skills/learn { skill }` (validated: tier, top rank, points from the server-side XP) and `POST /api/skills/respec` (free once, then `RESPEC_COST` coins). Both reply `{ ok, account }`; the app adopts it (`skills/skillsApi.ts` → `useAccountStore.adoptAccount`). Sign-up never uploads skills.
  - XP / coin bonuses are added in `/api/account/sync`, inside the daily caps; grants with `source: 'merge'` (guest progress at sign-in) get none.
  - Builder / Steward effects: the server sets `plot.mods = plotMods(ranks)` on every plot load and never stores it; every rule in `shared/src/plot.ts` reads it (`modsOf`, `buildMinutes`, `buyPrice`, `sellPrice`, `builderCount`, `storeCap`, `waterSupply`, `scrollCutMs`, Seven good years via `boostUntil`). Weekly perks: `POST /api/plot/cedar` and `POST /api/plot/instant`.
  - Quiz gifts are client-side, **Bible Blitz and Practice only** (`skills/giftStore.ts`, `GiftBar.tsx`; ranks come from `skills/mySkills.ts` to avoid an import cycle). `QuestionView` takes optional `giftBar` / `removed` / `hint` / `votes` / `doubled` props; the arena never passes them.
  - Screen: `screens/SkillTreeScreen.tsx` (styles in `theme/skills.css`), opened with `openSkillTree(from)` (`skills/nav.ts`) from Profile and from the top bar's gold seal when points are unspent.

## Deployment

See `docs/deploy.md`. The recommended setup is one Fly.io machine (`Dockerfile`, `fly.toml`); deploy with `fly deploy --ha=false`. Rooms live in memory, so it must always be **exactly one instance**, with a persistent volume at `/data` for the accounts database.
